# 源码组织、测试分离与注释规范

状态：从本规范落地起适用于新增和修改代码。既有代码按需求 0025 的 R0 分批迁移。
本文件是规范唯一来源；Agent 指南、模块文档只链接，不复制维护。

## 目录与职责

- `crates/` 放可复用 Rust 库；一个模块围绕一个职责，不按每个类型拆 crate。
- `services/` 放常驻服务入口，仅负责配置、依赖装配、监听和关闭。
- `apps/` 放交互式客户端；TUI/Desktop/Agent 客户端通过 Server 通信。
- 一次性 CLI 本进程执行，无需 Server；领域逻辑复用 crate。
- `lib.rs` 以模块说明、模块声明、对外导出为主；`main.rs` 保持薄装配层。
- 按职责命名模块，如 coordinator、session、execution、rpc、mapping；避免杂项 utils。
- 文件超过约 400 行或承载多个独立职责时检查拆分机会；行数是审查信号，
  不是硬性要求，不为减少行数把紧密逻辑切成难以追踪的碎片。
- 可见性最小化；测试需要访问私有实现时用子模块，禁止单纯为测试扩大 public API。

## 生产源码与测试必须分文件

生产文件不得含 inline `mod tests { ... }`、测试函数、Mock 或仅测试使用的辅助实现。
允许保留测试模块声明；测试专用 import 放到测试文件中。

```text
src/
├── lib.rs
├── tests.rs              # lib.rs 的模块单测
├── step.rs               # Step 生产实现
└── step/
    ├── tests.rs          # Step 单测
    └── tests/            # 必要时细分测试场景
        └── streaming.rs
```

生产文件末尾仅保留：

```rust
#[cfg(test)]
mod tests;
```

`step.rs` 中的声明对应 `step/tests.rs`；`lib.rs` 对应 `src/tests.rs`。
遵循 Rust 默认模块路径，不重复声明同一测试模块。测试文件可通过 `use super::*`
访问所属模块的私有实现。共享测试辅助代码放测试子树，避免依赖生产代码的测试实现。
同样原则适用于后续其他语言：遵循该语言惯用的独立测试目录/文件名。

- 局部单测：模块自己的独立测试文件。
- 跨 crate、真实 Provider、进程级测试：`kolyan-integration-tests/tests/`，按模块分类。
- 场景、请求和预期轨迹：独立 fixtures/expected；框架负责执行和比较。
- 原始日志与实际轨迹由测试代码写临时目录，不在正常 Step/Turn 内写测试文件。
- Rustdoc 示例用于 API 使用说明，可以保留；复杂测试与 mock 不放进 doc comment。
- 迁移测试仅移动和调整路径/import，不删除、降级或修改旧断言来获得通过。

## Rust 文件内的阅读顺序

默认按以下顺序组织，缺项直接省略：

1. `//!` 模块职责、边界与必要的不变量。
2. 必要的模块级属性；生产子模块声明及 `pub use` 公共导出。
3. `use`：标准库、第三方依赖、workspace crate、本模块；各组空行分隔。
4. 模块常量和类型别名；只服务局部算法的常量放使用处。
5. 数据契约：配置、请求/响应、事件/状态、错误；按依赖和领域阅读顺序排列。
6. 接口 trait：依赖端口和执行契约。
7. 主要实现类型及其 impl；构造 → 配置 → 公共操作 → 私有流程。
8. Trait impl：紧邻对应类型的 inherent impl，包括 Default/转换实现。
9. 局部辅助函数：紧随主要调用流程，校验、映射、编码按调用顺序组织。
10. `#[cfg(test)] mod tests;` 声明。

类型及其实现优先就近，多个大类型应拆模块，不把所有 impl 堆到文件底部。
编解码器可按 encode/decode 对称成组；状态机按实际转移顺序；不要按字母排序业务方法。
格式由 rustfmt 决定，不用手工对齐或长分隔线制造结构。

## 函数与可读性

- 对外入口先展示主流程；参数校验、准入、执行、提交、收尾顺序明确。
- 使用领域名称；布尔参数无法自解释时使用 enum/config，不使用连续位置布尔值。
- 错误显式传播并保留原因；不可用 `.ok()`、默认空值或空对象掩盖执行失败。
- I/O、状态写入与纯映射分清职责；资源/任务释放应覆盖错误、取消和 future 被丢弃。
- 异步函数中的阻塞 I/O 要明确处理，不用 async 包装同步操作来宣称并行。
- 重复领域类型应先确认所有权，避免 Server、Runtime 各自定义相同身份与状态规则。
- 新模块提供清晰的 public 导出；不要要求调用方依赖内部目录布局。

## 注释规范

- `//!`：说明模块做什么、依赖谁、不负责什么；复杂模块注明关键生命周期。
- `///`：公开 API 的契约，说明输入约束、返回语义、副作用、幂等性。
  涉及异步和持久化的 API 补充取消、重试、恢复语义；有实际需要才写
  `# Errors`、`# Panics`、示例，避免空模板。
- `//`：说明为什么这样实现、必须保持的不变量、协议兼容依据或非显然取舍。
  不重复函数名或逐行翻译代码。
- Rust 源码说明默认用英文；需求/架构文档默认中文；测试输入保留实际场景语言。
- 注释与代码一起更新；禁止把“全部通过”“已解决”等运行结果当永久代码注释。
- 新项目开发不保留旧接口、旧格式的兼容分支；契约变更迁移所有调用方。
  厂商协议映射和模型特性表是当前接入契约，不是历史兼容层；注明官方依据及验证场景。
  未经复现不能写“某模型总是如此”。
- TODO/FIXME 必须带可追踪需求或 issue、具体缺口和完成条件，不能留下泛泛的“以后优化”。
- 不写密钥、真实用户数据、完整生产请求；示例使用虚构数据。

示例：

```rust
// Preserve partial UTF-8 bytes until the next chunk completes the SSE frame.
// R1 / 0025: decoding each network chunk independently corrupts split characters.
```

## 审查与验证

代码审查检查职责、阅读顺序、测试分离及注释与行为是否一致。
纯文档变更检查链接和差异；纯测试迁移对比测试清单并运行对应测试。
行为变更执行模块回归和受影响集成/真实测试，具体以测试策略及需求验收为准。
`scripts/check-source-layout.sh` 已接入统一检查，拦截生产文件中的 inline tests 和
常用 test 属性；它是轻量文本检查，不是 Rust 语法解析器。文档路径自动检查尚待实现。
